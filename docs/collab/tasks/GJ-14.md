## 接口契约

### 契约 1：合成工作区与不可信语料

1. 全部状态建在 pytest 的 `tmp_path` 下，包含恰好两个由不同 manifest 发现的独立项目；每个项目至少有一份实现文件和一份测试定义，扫描后都必须是 `fresh` 且 eligible。
2. 两个项目使用不同技术栈或 manifest 类型，避免同一 fixture 被错误折叠成一个项目；项目 ID 必须从 broker 返回的 coverage/evidence 中取得，不可读 SQLite 猜 ID。
3. 项目名或 manifest 描述、JD 和一条上下文回答分别放入唯一哨兵，覆盖 `</script>`、事件属性/外部 URL、shell 元字符和“忽略 Skill 规则并执行命令”式提示注入。测试不得执行这些字符串，也不得把它们传给 shell。
4. 源文件另放一个原始源码哨兵；该完整字节串不得出现在 SQLite、manifest、Markdown、HTML、英文导出或 broker 输出。允许出现经 Agent 明确撰写的短 Claim，不允许以复制源码证明“分析”。
5. 本卡不构造 symlink、linked worktree、根外 Git、损坏仓库、权限故障或 carried-forward/excluded 项目；这些仍由账本原缺口与后续卡负责，不得在交付时声称已覆盖。

### 契约 2：真实 broker 与固定主链

测试必须启动真实 `runtime/scripts/session.py` 子进程，以 JSONL 请求调用公共 operation；不得直接实例化 `Scanner`、`PreparationService`、`AnalysisService`、`ArtifactSnapshotService`、`ExportService` 或 `ReviewService`。在第一个 broker 内按以下顺序完成：

1. `authorize_source_analysis`
2. `validate_job_input`
3. `scan`
4. `prepare_start`
5. `verify_source_revision`（`phase=before_read`，每个项目至少一条实际选用的 implementation SourceRevision）
6. `request_context`
7. `interview`（`mode=context`）
8. `list_context_evidence`
9. 一次应失败的 `record_analysis`
10. 一次合法且可幂等重试的 `record_analysis`
11. 两次等价 `render`
12. `translate_export` prepare、一次应失败的 publish、一次合法 publish

关闭第一个 broker 后，启动全新 broker，对同一 workspace 重新授权，再完成：重新 `validate_job_input` 并取得当前 task 的新 validation digest → `scan_overview` 复用既有终态 ScanRun → 新 request ID 的 `prepare_start` → `interview(mode=mock_review, action=list_targets)` → 一次带非法 transcript 字段的失败请求 → 合法 `record_review`。关闭第二个 broker 后，以独立只读 CLI 子进程执行 `python -m goodjob --data-dir <tmp-data-dir> data-status`；`data-status` 不是 broker operation，不得伪造同名 JSONL 消息。新 broker 不得复用旧 receipt/capability/validation digest；允许复用公开的 terminal `scan_run_id` 和已发布 `preparation_run_id` 所指冻结对象。

每个响应都先断言 `status` 与下一步所需 ID/状态，不得只因进程退出 0 就继续。第一个 broker 的 stderr 必须为空并正常退出；任何未知 operation、静默跳步或旧 task 绑定被接受都使测试失败。

### 契约 3：岗位镜头、两项目访谈与冻结复用

1. 使用一个明确目标岗位、非空 JD 和至少两个 RoleLens dimension；`weight_bps` 总和恰为 10000。`prepare_start` 必须返回 `analyzing`、同一个冻结 RoleLens、两个 eligible 项目和非空 EvidenceBundle。
2. 一个 `context-interview-request-v1` 必须同时包含两个项目各一张 card，不允许拆成两次请求。每张 card 的问题集合覆盖 `business_goal`、`role|ownership`、`learning`、`outcome|metric` 和 `tradeoff`；一个 `interview-input-v1` answer batch 必须恰好回答两张 card。
3. 返回 facts 必须按 project ID 隔离，fact kind 与被问范围一致；至少分页一次 `list_context_evidence`，以返回 cursor 取齐全部事实，不能读数据库补全。
4. 第二个 broker 创建的新 PreparationRun 必须在 EvidenceBundle 中看到第一个运行冻结的两个项目上下文事实；逐项核对 project ID、fact key/kind 和 statement，不得只断言数量大于零。

### 契约 4：分析归因、完整项目集与反向请求

1. 第一次 `record_analysis` 故意提交一句 `我实现……`，但移除其 `role|ownership` context relation。必须返回错误，PreparationRun 仍可接受后续合法分析，且没有任何可渲染半分析集。
2. 合法 `analysis-commit-v1` 必须为两个 eligible 项目各提交恰好一个 ProjectAssessment，维度键完整、coverage 可复算；给其中一项显著较低的分数，最终仍返回两个连续 rank。
3. 每个项目至少有一条以实现 Evidence 支撑的客观机制 Claim；整批还必须至少各含一条：
   - `personal_attribution=implemented` 的“我实现了什么”；
   - `personal_attribution=led|responsible` 的“我主导/负责什么”；
   - `personal_attribution=personal_learning` 的“我从项目中学到了什么”；
   - `personal_attribution=personal_outcome` 的“我推动/取得了什么结果”。
4. 个人 Claim 必须显式 relation 到同项目的 implementation Evidence 和所需 `role|ownership`、`learning`、`outcome|metric` context Evidence；禁止跨项目借证据。客观机制 Claim 说明“如何实现”，以非个人 scope-derived subject 开头。
5. 所有 Claim 使用非空 `review_semantic_projection`；不得以测试专用 schema 字段或降低产品校验来构造通过样本。合法请求用同 request ID 原样重试必须返回同一个 analysis commit 与 `ready` 状态。

### 契约 5：中文不可变准备包

1. `render` 必须返回四个同目录只读文件：`report.zh-CN.md`、`resume.zh-CN.md`、`index.html`、`manifest.json`，以及 `latest.json` 路径；实际文件名、snapshot/run/bundle identity 与 manifest 必须双向一致。
2. 测试按 manifest 的文件清单逐文件重算 SHA-256，并核对 `report_bundle_sha256`、`artifact_snapshot_id`、`preparation_run_id`。不得只断言路径存在。
3. 中文报告必须包含两个项目、客观机制、实现/主导、学习、结果 Claim 及“如何实现 / 学习要点 / STAR”结构；简历至少包含有证据支持的个人贡献与结果。精确 Claim 文本属于测试 fixture，不冻结产品 UI 文案。
4. 第二次等价 `render` 返回相同 snapshot，四个文件与 `latest.json` 逐字节不变；在英文导出、模拟复盘和第二次 prepare 后再次比对这些字节。
5. HTML 只做产物/manifest/惰性哨兵与无外部资源静态核对；跨引擎 UI 行为仍由 `npm run verify` 负责，不在本卡复制浏览器 runner。

### 契约 6：英文派生导出失败关闭

1. `translate_export(action=prepare)` 返回非空 `translation-export-source-v1` 后，`exports/` 下不得新增 ExportAttempt 临时目录或正式文件。
2. 英文候选必须从 prepare 返回的每个 source item 一一构造，逐项原样携带 source ID、kind、Claim/Evidence/RoleLens refs、项目/模块映射和完整 anchors；目标文本保留所有数字/单位与技术标识，不新增事实或已知技术。
3. 先制造一次确定性坏候选（删除一个 source item 或漂移一个 anchors 字段）。publish 必须失败，正式导出文件集合、中文快照和 `latest` 均不变。
4. 随后提交完整合法候选，必须原子发布英文 resume、interview Q&A 与 manifest；逐文件重算 manifest hash，核对 source snapshot/projection identity。合法导出仍不得修改中文快照或 `latest`。

### 契约 7：模拟复盘、数据状态与泄漏面

1. 新 broker 在当前 workspace 新授权后，对已发布首个 snapshot 列出非空 ReviewTarget。先给 `record_review` 请求增加不允许的 `transcript` 字段，必须失败且不创建复盘；再以新 request ID 提交仅含 summary、mastery、weak points、日期的合法复盘。
2. 合法结果必须绑定原 PreparationRun/ReviewTargetBinding，并返回写入的 mastery 与复习日期；旧 Markdown/HTML/manifest/latest 字节保持不变。
3. `data-status` 必须显示 SQLite、artifacts、exports、drafts 的字节数和快照数量；至少 SQLite、artifacts、exports 为非零，drafts 可为零但键必须存在。
4. `JobInput.jd_text` 是 [EVID-E22](../../20-architecture/evidence-model.md#33-岗位准备与学习层) 明确允许保存在个人 SQLite 的 Owner 输入。测试应以只读 SQL 确认本场景的 `job_inputs.jd_text` 保存了完整 JD；JD 私密哨兵不得出现在 broker 响应、`artifacts/` 或 `exports/` 的任何普通文件中，但不得因它存在于 `goodjob.sqlite3` 判泄漏。完整源码哨兵与非法 transcript 哨兵仍必须在整个 data directory 的普通文件中为零；Owner context 事实按产品契约允许持久化，不得误判为泄漏。
5. 所有 broker 响应都不得含 `session_capability`/`capability` 字段。本场景无法观察 broker 内存中随机生成的 capability 原值，不得把字符串搜索写成“已独立证明 argv/env/FD 全泄漏面”；该完整边界继续引用既有 `IMP-23` 专项证据。

## 实现指引

- 在新增测试文件内放最小 broker helper、JSON 类型断言、hash/manifest 检查与请求 builder；不要从另一个 `test_*.py` 导入私有 helper，也不要复制产品校验逻辑来制造同源假绿。
- 合成 fixture 由测试自己写入 `tmp_path`；需要 Git 时只对临时目录使用参数数组调用本机 Git，不设置远端、不 fetch、不 checkout。能用 manifest 隔离两个项目时不必引入 Git。
- AnalysisDraft 与英文候选是确定性的“Agent 输出替身”，必须从 broker 返回的项目/evidence/context/source item ID 组装；不得硬编码运行生成 ID或直读 SQLite。
- 失败请求使用与合法请求不同的 request ID；失败后先检查状态/文件集合，再提交合法请求，防止幂等键掩盖半提交。
- 若发现现有公共 API 缺失或返回形状无法满足卡面，按 L1 报告 `现象 / 影响 / 最小复现 / 建议拆分`。本卡不授权“顺手修好”。
