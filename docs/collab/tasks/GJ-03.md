## 背景（为什么做）

契约指针：[扫描与分析设计 §2.2 与 §4.3](../../20-architecture/scanning-and-analysis.md)、`D-034`（已收窄）、`F-009`、`SCAN-04`。

`config.toml` 由 `paths.py` 创建后从未被任何代码读取。`snapshot_disposition='excluded'` 在 schema CHECK、覆盖聚合、`reporting._DISPOSITIONS`、看板图例和 `IMP-13` 场景中全部就位，但没有任何代码路径写入它。`scanner.py` 在文件超限时还提示用户 "Add a narrow safe exception"，指向一个不存在的机制。

**Owner 已决**：只做项目级排除。精确到文件路径的安全例外收窄为 `F-009`，不进入首版——它是唯一会让扫描读到本来被排除内容的入口，需要独立设计秘密拒绝校验、例外命中审计与覆盖呈现。

## 目标（做成什么样）

Owner 在个人数据目录的 `config.toml` 中登记项目级排除规则后：命中的项目在本次 `ScanRun` 记为 `excluded`，不创建快照、不产生 Evidence、不进入合资格集合；覆盖摘要能让 Owner 看出哪个项目因哪条规则被排除，并与 `failed_no_baseline` 分开呈现。配置出问题时扫描继续并可见。

## 涉及范围

- **允许**：`runtime/src/goodjob/paths.py`、`runtime/src/goodjob/scanner.py`、`runtime/tests/test_scanner.py`、`runtime/tests/test_installation.py`；若确需新增配置解析模块，允许新增 `runtime/src/goodjob/config.py` 及其测试
- **禁止**：其余一切文件。特别是 `db.py` 的 schema（`excluded` 取值已存在，不需要 migration）、`analysis.py`、`preparation.py`、`reporting.py`、`frontend/`
- 零新增依赖——Python 3.12 标准库有 `tomllib`，用它

## 接口契约

Architect 给定，不得擅改：

1. 配置文件仍是 `DataPaths.config_file`（`~/.codex/goodjob-career-review/config.toml`）。新增一个 `[[goodjob.excluded_projects]]` 数组表，每项字段：
   - `match`（必填）：`identity_key` 或 `relative_location` 二选一，声明按哪种方式匹配；
   - `value`（必填）：对应的匹配值，非空字符串；
   - `reason`（必填）：Owner 写的理由，非空字符串，用于覆盖摘要呈现。
2. 匹配在**项目发现完成之后、快照创建之前**进行。`relative_location` 按工作区相对位置精确匹配（规范化后逐字符相等），**不是通配、不是前缀**。
3. 命中项目写入 `ScanRunProject.snapshot_disposition='excluded'`，不创建 `ProjectSnapshot`、不产生 Evidence、不进入 `role_lens_context` 的合资格集合。
4. 覆盖摘要新增排除项列表，每项含 project 显示名、命中的 `match`/`value`、`reason`。`excluded` 计数与 `failed_no_baseline` 计数保持各自独立的字段，不合并。
5. 配置不可读、TOML 解析失败、字段缺失/类型错误、或规则的 `value` 未命中任何已发现项目时：产生 `ScanIssue`（severity `warning`），**扫描继续**，其余规则照常生效。整份配置不因单条规则出错被丢弃，扫描也不因配置问题终态 `failed`。
6. `config_revision` 已是 `scan`/`refresh` 的既有入参。排除规则变化必须能通过 `config_revision` 变更让受影响项目在下一次运行重新评估——**不要**新增自动侦测配置变化的机制。
7. `scanner.py` 中 `"Add a narrow safe exception only if this file is source material."` 这句补救提示删除，替换为当前真实可行的动作（例如提高 Owner 侧关注、或说明该文件超出本地索引上限且不影响其他文件）。

## 实现指引

- 配置读取放在 `scan`/`refresh` 入口一次性完成，把解析结果作为值对象传进扫描流程，不要在遍历中反复读文件。
- `identity_key` 对 Git 项目是规范化 common-dir 实路径，对非 Git 项目是项目根实路径——见 `projects` 表的 `identity_kind`/`identity_key`。Owner 用 `relative_location` 的场景更常见，两种都要支持。
- 排除判定发生在项目已被发现之后，所以被排除项目仍有稳定 identity，可以正常写 `ScanRunProject` 行。
- 测试用 `data_paths` fixture 指向 tmp 目录，直接写 `config.toml` 内容即可，不需要真实用户目录。

## 边界与禁区

- **不要顺手实现文件级安全例外（`F-009`）**。排除只能减少读取范围；任何"让扫描读到本来读不到的内容"的能力都超出本卡，且属于安全边界红区。
- 不新增 schema migration——`excluded` 已在 CHECK 取值中。
- 不改 `config.toml` 承载的其他内容边界（工作区注册、项目身份、角色信息仍由 SQLite 持有）。
- 不新增运行时依赖。
- 不做配置文件的自动生成/迁移/写回——GoodJob 只读它。
- 卡面与实际代码矛盾时停工 L1。
