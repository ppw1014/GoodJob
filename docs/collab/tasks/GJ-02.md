## 背景（为什么做）

契约指针：[证据模型 §3](../../20-architecture/evidence-model.md) `ReportInlineToken` 段与其后的分层校验段、`EVID-INV-27`、[ADR-0008](../../30-decisions/adrs/ADR-0008-single-file-dashboard-and-structured-token-embedding.md) 决策 8、`D-043`。契约已定稿，本卡是让实现追上契约。

`_resolve_tokens` 把整条 token 序列 `join("")` 成一个字符串，`_detected_personal_attribution` 在这个字符串上跑正则；`_FIRST_PERSON_PATTERN` 含 `\b(?:I|my|me)\b` 且带 `IGNORECASE`。于是被 `code` token 引用的标识符和命令行片段会命中散文规则。实测两条纯客观陈述被判为 `personal_assertion`，并按批量原子性拒绝整份 `analysis-commit-v1`：

- `该项目通过 rg -i 做大小写不敏感检索并汇总候选文件。`
- `该项目在遍历中使用 for (i = 0; i < n; i++) 控制候选批次。`

错误信息是 `Claim statement contains stronger personal attribution than declared`，对一条没有任何个人化表述的陈述无法自解释；而 `record_analysis` 是全或无的，代价是一整轮分析。

`ReportInlineToken` 的封闭 kind 集合本来就是为了让接收方按 kind 区别对待，这里恰好在最需要结构的地方把结构丢了。

## 目标（做成什么样）

引用了标识符、路径或命令行片段的非个人化 Claim 能正常通过 `record_analysis`；同时全部既有归因门槛一条不降——`code` token 不能成为规避归因校验的通道。

## 接口契约

Architect 给定，不得擅改：

1. 散文级判定**只作用于 `text` 与 `emphasis` 两种 kind 的 `value`**。`code`、`inert_url`、`claim_ref`、`evidence_ref`、`gap_ref` 的 `value` 不参与散文判定。适用范围包括 `_PERSONAL_PATTERNS`、`_OMITTED_SUBJECT_PERSONAL_PATTERNS`、`_FIRST_PERSON_PATTERN` 的全部匹配。
2. 非个人化主语核对**不变**：仍要求首个 token 的 kind 为 `text` 且其**完整值**等于 `scope_kind` 派生的主语（`project=该项目` / `worktree=该工作树` / `module=该模块`）。
3. `_OMITTED_SUBJECT_PERSONAL_PATTERNS` 的 `^` 锚定语义按分层后重新界定并在代码注释中写清：它锚定到**参与散文判定的文本序列的开头**，而不是拼接全串的开头。
4. `_resolve_tokens` 现有的第二个返回值（拼接全串）如仍被其他调用方使用（如 `statement` 落库、`review_semantic_projection` 的 fallback），**保持不变**；本卡只改散文判定的取值口径，不改持久化的 statement 形态。
5. 拒绝时抛出的错误类型与消息语义不变。

## 实现指引

- 最小改法是在 `_resolve_tokens` 旁增加一个只取散文 kind 的投影，供归因校验使用；不要改 `_resolve_tokens` 的既有返回契约（见契约 4）。
- 分层后 `code` token 里的 `我实现了` 不会再命中散文规则——这是允许的，因为 `code` 不是散文载体，而主语核对（契约 2）仍然拦住把个人化主张塞进首 token 的做法。DoD 里有对应的反向用例，确认这条边界是被断言过的。
- 顺带核查 `analysis.py` / `exporting.py` 中其他作用在拼接文本上的规则（`_reject_verbatim_source_summary`、英文导出的事实锚点校验）：**只核查并在交付报告中说明它们的作用域是有意为之还是同类疏忽，本卡不改它们**。若判定为同类疏忽，按 L2 上报，由 Architect 决定是否另开卡。
