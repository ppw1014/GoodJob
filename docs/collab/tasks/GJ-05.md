## 背景（为什么做）

契约指针：[扫描与分析设计 §4.1](../../20-architecture/scanning-and-analysis.md)、`D-014`（已补充子集条款）、`SCAN-04`、`IMP-04`。

`IgnoreMatcher` 的 docstring 自称 "a deliberately small, deterministic subset of .gitignore semantics"，但这个差异只写在代码注释里，文档、覆盖摘要和 ScanIssue 都不体现。已确认的偏差至少三类：

- `line.strip("/")` 同时抹掉了根锚定，`/build` 会误伤嵌套的 `build/`（过度排除）；
- `!` 反选按"最后命中生效"，可以重新纳入 Git 本来会忽略的内容（过度纳入，Git 明确规定被排除目录下的文件无法重新纳入）；
- `fnmatch` 的 `*` 跨 `/` 匹配，`src/*.py` 会命中 `src/a/b.py`（过度排除，Git 的 `*` 不跨路径分隔符）。

"非忽略内容均可成为证据"是文档里的诚实性承诺，静默的近似匹配会让它在个别工作区不成立。

## 目标（做成什么样）

ignore 匹配的能力边界是被显式列举、被测试锁定、且对 Owner 可见的：遇到已知不支持的模式语法时，Owner 能从覆盖摘要看到"这条规则被按什么近似语义处理了"，而不是拿到一份看起来完整、实则悄悄多排或少排的证据集。

## 涉及范围

- **允许**：`runtime/src/goodjob/scanner.py`（`IgnoreMatcher` 及其调用点、ScanIssue 与覆盖摘要相关部分）、`runtime/tests/test_scanner.py`
- **禁止**：其余一切文件。特别是 `docs/`（契约已定稿）、`db.py`、`analysis.py`、`preparation.py`、`reporting.py`、`frontend/`
- 零新增依赖——**不得引入第三方 gitignore 库**（运行时 `dependencies = []` 是刻意的供应链边界，红区）

## 接口契约

Architect 给定，不得擅改：

1. 在 `IgnoreMatcher` 中**显式列举**支持的模式语法范围（代码常量或结构化定义，不是散文注释），至少覆盖：字面名、`*`/`?` 通配、目录后缀 `/`、否定前缀 `!`、含 `/` 的路径型模式、注释与空行。
2. **命中不确定时偏向排除，不偏向纳入**。这是既有行为倾向，本卡把它固化为被断言的规则。
3. 遇到已知不支持的语法产生 `ignore_pattern_unsupported` 类 `ScanIssue`（severity `warning`），字段必须说明：来源 ignore 文件的相对路径、原始模式行、以及**该模式实际被按什么近似语义处理**。至少覆盖这三种：
   - 根锚定 `/pattern`（被按"任意层级同名"处理）；
   - 已排除目录下的 `!` 反选（被按"重新纳入"处理，与 Git 不一致）；
   - `**` 语法（说明其实际匹配行为）。
4. 上述 ScanIssue 进入覆盖摘要，Owner 能看出"哪些内容因为哪条规则没有进入证据"。
5. **本卡不修正这三类偏差的行为**，只做显式化 + 可见化 + 测试锁定。是否改为与 Git 等价，取决于本卡交付后 Owner 的裁决；若实现侧认为某一类应当直接修正，按 L3 建议提出，**裁决前不得按建议实现**。
6. `IgnoreMatcher.matches` 的签名与返回类型不变。

## 实现指引

- 判定"是否为不支持的语法"应在 `load` 阶段做（那时能拿到原始行与来源文件），不要放到 `matches` 的热路径里。
- 现有 `load` 已经返回 `(matcher, issues)`，新 issue 走同一通道即可。
- 契约 5 是本卡最容易越界的地方：写测试锁定当前语义时，如果发现"当前语义"其实是个 bug，正确动作是**照实锁定 + L3 上报**，不是顺手改对。
