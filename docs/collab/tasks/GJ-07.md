## 背景（为什么做）

契约指针：[验收基线 §1](../../40-delivery/acceptance-baseline.md)、[ADR-0008](../../30-decisions/adrs/ADR-0008-single-file-dashboard-and-structured-token-embedding.md) 决策 8。

门禁目前是**六条要人手敲的命令**，分散在两个目录，只写在 README 里。仓库根没有 `Makefile`、没有 `justfile`、没有 CI 配置。

这不只是"敲起来麻烦"。`dashboard.js` / `dashboard.css` 是从 `frontend/src/*.ts` 构建出来、**提交进仓库**的产物，Python 侧运行时直接读它们。我在 2026-07-31 做了实测：改 `frontend/src/dashboard.ts` 里一句 UI 文案、**不重新构建**，然后跑全套门禁——

```text
uv run pytest -q（180 个用例）      -> 绿
npm run verify（跨引擎行为门禁）    -> 绿
npm run build:check                -> 红
```

`npm run verify` 也是绿的，因为它调用 Python 的 `render_dashboard_html`，而后者读的同样是**已提交的产物**，不感知 TypeScript 源码。

也就是说：**全套门禁里只有 `build:check` 这一条知道源码与产物是否还对得上，而它挂在需要浏览器准备步骤的那条链子上。**漏敲一次 `npm test`，源码与产物就能静默分叉，而且分叉之后所有其他门禁继续全绿。

## 目标（做成什么样）

仓库根一条命令跑完日常门禁，退出码即结论，任何一条子门禁失败都能一眼看出是哪条；构建漂移落在这条命令的覆盖范围之内。

## 涉及范围

- **允许**：仓库根新增 `Makefile`；仓库根新增 `scripts/check-doc-links.py`（信道 #18 裁决新增）；`README.md` 的「本地开发」段
- **禁止**：其余一切文件。特别是 `runtime/` 下的任何源码与测试、`package.json` 的 scripts、`pyproject.toml`、`docs/` 下的契约文档（**含 `protocol.md` 本身——本卡对齐它，不修改它**）
- **零新增依赖**：不装 `just` / `task` / `nox` / `tox` / `pre-commit` / `make` 的任何替代品。本机 GNU Make 3.81 已就位，用它

## 接口契约

Architect 给定，不得擅改：

1. 入口是仓库根的 `Makefile`。**不用 shell 脚本**：Make 的目标依赖关系是声明式的，且自带 `-n` 干跑，Owner 能在执行前看清将要跑什么。
2. **目标集合必须完整覆盖 [protocol §8 门禁命令表](../protocol.md) 的全部三族，逐条一致——不增、不减、不改写。**（信道 #17 L1 → #18 裁决重写；原条款按族别手工枚举，枚举本身不完整，是本次 L1 的根因。改为以协议表为唯一事实源。）目标命名固定：
   - `make gate-python`——协议表 Python 族四条，在 `runtime/` 下执行。
   - `make gate-frontend`——协议表前端族，在 `runtime/frontend/` 下执行。协议表原文是 `npm ci && npm test`，**`npm ci` 不得省略**；两条写成**独立配方行**以保留失败定位。
   - `make gate-docs`——协议表文档族：全仓 markdown 相对链接检查，断链为零。该族目前**没有任何可执行命令存在**，只作为约定由人手工执行，故本卡须新建 `scripts/check-doc-links.py`（见契约 8）。
   - `make gate`——上面三个的聚合。**不含** `npm run verify`。
   - `make gate-release`——`gate` 之上再加 `npm run verify` 与 `uv build`。
3. **`make gate` 必须同时覆盖两条静默漂移路径**，且都要由 DoD 自检证明，不能只靠推理：
   - 源码与已提交产物的漂移（由 `npm test` 内的 `build:check` 接住）；
   - 依赖清单与已安装 `node_modules` 的漂移（由 `npm ci` 接住）。第二条正是省略 `npm ci` 会新开的口子——本卡若在这里留缺口，等于一边堵漂移一边造漂移。
4. 任一子命令失败时，`make` 以**非零退出**，且输出能定位到是哪一条子门禁失败。**不得**用 `-` 前缀忽略错误、不得 `|| true`、不得把多条命令用 `;` 串成一条掩盖中间失败。
5. **不改任何门禁命令本身**：不放宽参数、不删条目、不调换 `npm test` 内部的既有顺序。本卡只做聚合，不做取舍。**契约 2 与本条冲突时以 protocol §8 为准**——协议是共同事实源，卡面是它的下游。（#17 L1 拦下的就是这个：原契约 2 把前端族写成 `npm test`，与协议表的 `npm ci && npm test` 不一致，于是契约 2 自己成了「改门禁命令」。）
6. `npm run verify` 保持在日常门禁之外（[GJ-04](GJ-04.md) 契约 8 已裁决：浏览器二进制属本机发布前依赖）。**不得**把它并进 `make gate`。
7. `README.md` 的「本地开发」段改为以 `make` 为主入口，**同时保留**展开后的原始命令清单——Owner 常常只想跑其中一条，聚合不应该把单条命令藏起来。
8. `scripts/check-doc-links.py`：**只用 Python 3 标准库**，零依赖，不进 `runtime/` 包。行为固定为——扫描全仓 `*.md`，取出 markdown 行内链接，跳过 `http`/`https`/`mailto` 与纯锚点，其余去掉 `#` 锚点后按**相对于该 md 文件所在目录**解析，目标不存在即为断链。有断链时逐条打印「文件:目标」并以非零退出；无断链时打印检查的文件数并以 0 退出。
9. **检查器必须跳过代码区**：围栏代码块（``` 与 ~~~）与行内代码之内的内容不参与链接提取。理由是实测出来的——本卡面与信道里就有描述链接语法的示例文本，天真的正则会把它们当成真链接报断链，那样门禁会因为文档在讲解链接语法而变红。这条不是可选的健壮性加分项，是本检查器能否在本仓库跑通的前提。

## 实现指引

- 两个门禁目录不同（`runtime/` 与 `runtime/frontend/`），用 `$(MAKE) -C` 或在配方里 `cd`，两种都可以，选一种写清楚。
- Make 的每一行配方是独立 shell，`cd` 不跨行保留——这是最容易踩的坑。
- 目标都不产出文件，记得声明 `.PHONY`。
- `npx playwright install webkit chromium` 是一次性准备步骤，不要放进任何 `gate*` 目标里——那会让门禁在网络不通时失败。README 里保留它作为前置说明即可。
