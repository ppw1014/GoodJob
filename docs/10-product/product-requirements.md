## 1. 产品边界与默认值

GoodJob 是由 host agent 显式调用的个人职业准备 Skill，而不是一个自动后台扫描服务或独立桌面程序。一次准备运行围绕**一个主岗位**和**一个工作区根**组织；用户可以对不同工作区或不同岗位分别创建准备运行，但首版不生成多岗位并排比较报告。

以下默认值是首版固定契约：

| 项 | 默认值 |
| --- | --- |
| 调用入口 | `$goodjob-career-review` 显式发起；不在未调用时读取工作区。 |
| 工作区输入 | 一次运行使用一个用户指定、存在且可读的目录作为根；该根下的所有可识别项目和模块进入候选范围。 |
| 岗位输入 | `target_role` 为必填自由文本，不受预置岗位枚举限制。 |
| JD 与职级 | `job_description` 可选，接受粘贴文本或一个本地可读文件；`level_override` 可选且优先于 JD 推断的职级。 |
| 语言 | 中文为首版主包语言；英文简历与英文问答按需从同一中文快照导出。 |
| 项目事实 | 当前可读工作树优先于历史描述；初始 Git 历史窗口为最近 180 天，只有具体 Claim 需要时才向更早历史追溯。 |
| 刷新 | 首次全量扫描，之后只由用户显式触发 `refresh`；不建立文件监听或定时任务。 |
| 深读 | 首版深读 TS/TSX、Python、Rust、Dart、SQL；其余语言保留可靠基础档案和可见的能力边界。 |
| 个人信息 | 工作区注册、用户回答、SQLite、快照和复习状态位于 Skill 外的个人数据目录，不进入版本化 Skill 或 GitHub。 |
| 源码分析授权 | 每个 host agent task 生成不落库的易失 SessionCapability；每个显式 Skill 会话以其 binding digest 形成范围级 `AuthorizationReceipt`，能力丢失即重新确认。 |

其中 `target_role`、`job_description` 和 `level_override` 是一次运行的岗位输入；具体 RoleLens 字段和保存方式由 [证据模型](../20-architecture/evidence-model.md) 定义。

## 2. 用户流程

1. 用户显式调用 Skill，说明工作区路径和目标岗位；可同时提供 JD 与职级覆盖。
2. Skill 显示规范化工作区、将处理的源码/配置/文档/Git 元数据类别，以及“本地扫描器不新增上传，但 host agent 打开的原文件会进入当前会话的模型处理链路并受当前产品/账户/工作区策略约束”的提示；Owner 一次范围级确认后形成当次 `AuthorizationReceipt`，不逐条确认 Claim。
3. Skill 验证工作区和 JD 输入。显式指定但不可读的 JD 必须由 Owner 更正，或由 Owner 明确选择无 JD 模式后才可继续。
4. 扫描器发现项目、工作树和模块，建立或刷新本地证据索引；任何跳过、权限问题、未授权根外 Git 元数据或不支持能力被记录为可见问题。
5. host agent 根据岗位输入、可选 JD、岗位参考和证据生成并持久化本次 RoleLens；无 JD 时保留明确假设而不是停止。
6. 系统先对候选 SourceRevision 做准备预检，再从岗位相关证据包形成材料，并按具体问题深读本地原文件。预检、读取前或提交前发现内容变化时，明确要求 Owner refresh，不隐式重扫。
7. 系统生成并保存不可变中文岗位主快照（完整报告 Markdown、简历源稿和离线 HTML），并可显式导出可编辑工作稿；`latest` 指向最近一次成功的中文主快照。
8. 用户可继续进行模拟面试、记录复盘和下次复习日期，或从既有快照按需导出英文简历和英文问答。复习状态只在稳定目标及事实指纹兼容时显示为延续状态。

## 3. 功能需求

### FR-01：显式 Skill 入口与运行意图

Skill 必须通过 `$goodjob-career-review` 显式调用。首版支持“首次扫描/准备”“显式刷新”“基于既有快照继续模拟面试”“按需导出英文材料”四类对话意图。系统不得在未调用时扫描、监听或修改用户工作区。

在本会话第一次访问源码、源码衍生证据或既有项目材料前，Skill 必须显示工作区、处理类别、GoodJob 的本地处理边界，并明确说明 host agent 打开的原文件会进入当前会话所使用的模型处理链路、其处理与保留受当前产品/账户/工作区策略约束。Owner 必须确认其有权分析该范围且会自行审阅对外材料中的保密内容。路径具有读取权限不等于该确认；确认仅覆盖当前显式会话，不要求逐条确认 Claim。拒绝、缺失或提示版本变化时，系统不得创建新的 `ScanRun`、`PreparationRun`、`EvidenceBundle` 或模型驱动导出；既有离线产物仍可由 Owner 在本机直接打开。

“同一会话”由当前 host agent task 的易失 `SessionCapability` 技术绑定：编排运行时生成至少 256 bit 随机值并只持有原始值，SQLite 仅保存 domain-separated digest。每个受保护请求临时证明持有原始 capability；新 task、能力丢失、digest/scope/notice 不匹配都必须重新确认，不能仅凭 receipt ID 继续。原始 capability 不得进入 argv、环境变量、GoodJob 日志、数据库、产物或用户可见输出；host agent 对当前 task trace 的处理仍服从其既有边界。若运行时不能提供 task-scoped 易失状态，首版必须 fail closed。

**验收结果：** 用户能明确看到本次准备运行的工作区、主岗位、JD/职级输入状态、AuthorizationReceipt 状态和产物状态。

### FR-02：岗位与工作区输入

一次准备运行必须接受以下输入：

| 输入 | 必需性 | 契约 |
| --- | --- | --- |
| `workspace_path` | 必填 | 必须是本机存在且可读的目录。若根目录不可读，运行以明确输入错误结束，不伪造扫描结果。 |
| `target_role` | 必填 | 任意自由文本岗位名称，例如应用软件工程师、中间件工程师、架构师、系统工程师或未内置的新岗位。 |
| `job_description` | 可选 | 可为粘贴的 JD 文本或一个可读普通文本文件。若显式指定的文件不存在、是目录、无权限或无法安全解码，系统必须显示路径与原因；Owner 只能更正它，或明确选择 `continue_without_jd`。在该选择前，不得把它当作未提供 JD，也不得创建 JobInput、RoleLens 或 PreparationRun。 |
| `level_override` | 可选 | 用户明确指定的职级；存在时覆盖从 JD 推断的职级。 |
| 输出请求 | 可选 | 默认生成中文主包；用户可在同一快照上请求英文简历、英文问答或模拟面试。 |

默认岗位和项目级排除规则属于个人配置，不改变本次运行的显式输入优先级；工作区注册由本地状态库持有。首版没有把被忽略文件重新纳入的机制（`F-009`）。

### FR-03：跨项目与模块盘点

系统必须在 `workspace_path` 下发现并盘点所有可识别项目与模块，而不是只读取最近打开的仓库。它必须涵盖 Git 仓库、嵌套 Git 仓库、linked worktree 和可识别的非 Git 项目；同一 Git common-dir 的多个工作树合并为一个项目，但保留工作树、分支和 HEAD 来源。

系统必须把当前未忽略的已提交、已修改和未跟踪代码/文档纳入候选事实，并将其状态明确呈现。父仓库的忽略规则不得吞掉独立的嵌套仓库。发现、忽略、工作树归并和模块识别的完整技术契约见 [扫描与分析设计](../20-architecture/scanning-and-analysis.md)。

**验收结果：** 准备包中有覆盖清单，能区分项目、工作树、模块、已扫描范围和未覆盖范围。

### FR-04：全量首次扫描与显式增量刷新

首次对一个工作区扫描时，系统必须建立全量可用索引。后续仅在用户显式要求时 refresh，并基于文件/证据变化更新受影响的内容；不应把未变化的材料无依据地重新解释为新事实。

refresh 不得覆盖用户补充的项目背景、项目级访谈答案、历史准备快照或面试复盘。证据位置或内容哈希失效时，系统必须标记旧证据过期并要求重新读取，而不是静默沿用旧摘要。

`refresh` 默认采用 `fast` 变化检测：路径、大小、`mtime_ns` 与 Git 状态只用于筛选候选，已报告 `modified` 或 `untracked` 的合资格文件必须重新计算内容哈希；“无变化”仅表示未检测到变化。Owner 可显式选择 `verify_content`，使全部合资格文件重新计算 SHA-256；相同哈希可复用既有分析，不能因此重新深读全部文件。两种模式及其覆盖含义必须在运行结果中显示。

### FR-05：动态 RoleLens 与岗位差异化

每个准备运行必须形成一个持久化的 RoleLens。它由 `target_role`、JD、职级覆盖、通用岗位参考和项目证据共同生成，至少向用户展示：岗位名称、采用的职级、分析维度与相对权重、所需证据类别、项目排序依据、输出重点、面试问题策略、知识缺口规则和关键假设。

规则如下：

- 一个运行只使用一个主岗位。
- JD 存在时优先用于职级与要求解释；`level_override` 具有最高优先级。
- 没有 JD 时，系统仍须生成候选 RoleLens，并在材料中显式标明假设。
- 岗位参考框架只能辅助思考，不能把岗位限制成固定枚举；未知岗位仍应可运行。
- 同一证据图谱在不同岗位的独立运行中必须能够产生不同但可解释的项目排序、重点和面试问题。

### FR-06：技术、业务、实现与学习分析

系统必须围绕 RoleLens 对项目和模块形成以下四类材料，并以证据强度和状态区分确定结论与待补充内容：

| 维度 | 至少回答的问题 |
| --- | --- |
| 技术 | 使用了哪些语言、框架、依赖、数据存储、协议、部署或测试技术？它们是否在实际代码、配置或测试中出现？ |
| 业务 | 项目服务什么领域、用户流程、数据对象、外部接口或业务约束？证据不足时哪些业务背景尚不可知？ |
| 实现 | 模块承担什么职责、怎样协作、数据/控制如何流动、关键机制怎样实现、有哪些设计取舍和验证手段？ |
| 学习 | 用户应能重新掌握哪些概念、模式、调试/测试方法和系统取舍？哪些点还需要阅读、追问或练习？ |

扫描器负责结构化盘点，host agent 负责在岗位相关证据包基础上归纳；遇到具体问题时，host agent 必须能够继续打开本地原文件深读，而非仅依赖数据库摘要。

### FR-07：能力叙事、贡献叙事与结果边界

GoodJob 不要求用户对每个 Claim 逐条确认，但必须严格区分以下叙事层次：

| 层次 | 可用表述 | 允许证据 | 禁止行为 |
| --- | --- | --- | --- |
| 项目事实 | “项目/模块使用了……”“该流程实现了……” | 代码、配置、测试、文档等项目证据 | 把项目事实自动说成用户个人贡献。 |
| 能力叙事 | “我能讲解……”“我掌握/需要复习……” | 项目事实和基于事实的学习归纳 | 假装已拥有未能解释的实际交付成果。 |
| 贡献叙事 | “我实现了……”“我负责……”“我主导……” | 用户在项目级上下文中给出的责任范围，或可核验的个人角色证据 | 仅凭 Git 作者、提交数量或文件归属断言个人职责。 |
| 个人结果叙事 | “我推动/取得了……结果或指标” | 可核验的项目结果/指标 Evidence，加上能把该结果与用户职责关联的当前 role/ownership 上下文或个人角色 Evidence | 仅凭项目存在某个结果就把它归因给用户，或推测不存在的数字、业务价值和影响范围。 |

每个项目章节都必须帮助用户回答“我从中学到了什么、项目实现了什么、它如何实现、我可讲解到什么深度”。实现证据可以直接形成“可复习/可讲解的学习要点”；过去式“我当时学到了……”属于个人学习复盘，需要项目级 learning 上下文。若个人责任或学习背景尚缺，系统保留客观实现、能力叙事和候选学习要点，并把可升级的第一人称内容列入项目级访谈缺口；不得用未经证实的个人历史填充简历。

### FR-08：完整中文岗位准备包

一次成功准备运行必须生成一份完整中文岗位准备包，至少包含：

1. 本次输入、RoleLens、职级与假设、扫描覆盖范围和 ScanIssue 摘要。
2. 面向岗位的能力地图、项目排序与排序理由。
3. 每个入选项目的业务背景、模块地图、技术要点、可讲解架构/流程、实现方式、验证与取舍、学习要点、知识缺口和证据入口。
4. 每个项目的可用简历 bullet、STAR 素材、两分钟项目讲解、可能追问及回答要点；个人责任或结果不足时必须带状态说明。
5. 跨项目汇总的可编辑简历 Markdown 总稿、岗位面试题库和复习重点。

### FR-09：跨项目岗位能力地图与可追溯组织

系统必须先给出跨项目岗位能力地图和可解释的项目排序，再保留每个项目和模块的可追溯章节，避免只输出松散的技术清单。项目排序必须来自本次 RoleLens 的维度、权重和证据状态；排序较低或未入选重点项目不能被静默删除，必须仍可从覆盖清单进入其基础档案和缺口说明。

每个能力维度、项目优先级和项目章节必须能回到 Project、Module、Claim 与 Evidence 链路。不同岗位的独立运行可以改变排序与阅读重点，但不得改变同一项目的基础事实。

只有本次终态 ScanRun 中拥有 `fresh` 或 `carried_forward` ProjectSnapshot 的项目进入岗位评分并取得连续 rank；`failed_no_baseline` 与 `excluded` 项目只出现在覆盖清单、原因和补救动作中，不得以零分或空 Assessment 伪装为已比较项目。

### FR-10：项目级批量访谈

系统只在下列缺口会显著影响材料可信度时提问：业务目标/受众、量化或可验证结果、用户个人责任范围、关键决策背景。提问必须按**项目**聚合为一次批量访谈卡，列出多个高价值问题及其对应的待补足材料；不得把流程退化为对每个 Claim 的逐条确认。

用户回答后，系统必须把回答作为用户提供的项目上下文持久化并复用于后续 refresh、准备包和面试训练。用户可跳过问题；被跳过的内容保留为可见缺口，不阻塞其他项目产物，也不由模型补写。

### FR-11：证据可追溯与材料状态

每个关键技术、业务、简历或面试 Claim 必须能显示其项目、模块、文件位置、简短证据摘要和状态。状态至少要能让用户区分：已实现、存在测试定义、已有可核验测试通过结果、已文档化、仅计划、未提交工作区材料和用户补充信息。测试文件存在不能自动显示为测试已通过。

关键简历 bullet、STAR 素材和强个人表述必须回溯到对应 Claim；当原文件位置或哈希失效时，材料必须标记为需要 refresh，而不是继续显示为已核验。证据的字段和生命周期由 [证据模型](../20-architecture/evidence-model.md) 权威定义。

### FR-12：不可变快照、Markdown 与离线 HTML

每次成功准备运行必须保存一个不可变中文岗位主快照，并维护一个指向最新成功中文主快照的 `latest` 入口。用户补充和历史快照不得被后续 refresh 覆盖。

系统必须同时提供：

- 主快照内的完整 Markdown 报告与简历 Markdown 源稿，以及由用户显式导出的可编辑工作稿；后续 prepare/refresh 不得覆盖工作稿。
- 包含本次报告数据的离线静态 HTML 看板，支持浏览项目排序、长内容和证据展开，且不依赖常驻服务、HTTP API、远端 CDN 或运行时网络请求。

### FR-13：中文主包与按需英文导出

中文是首版主工作语言和完整准备包语言。用户可从一个既有中文主快照按需生成独立、不可变的英文简历与英文面试问答导出；英文导出必须保留与中文同一事实、RoleLens 和证据边界，不能在翻译时新增未证实成果，也不得修改源快照或 `latest`。每个英文 bullet 或问答必须回指冻结的中文 `source_item_id` 及其事实锚点；生成器必须校验请求的源/目标条目集合、数字/单位、技术标识、状态与角色/结果锚点的规范化等价，出现额外、缺失或被篡改的条目时整批失败。

翻译候选只存在当前 task 内存；首次文件写入前，单个发布子进程必须先创建 `ExportAttempt`，记录 owner process identity，并只在按 attempt ID 预登记的临时/最终路径写入。只有全部校验通过并原子发布成功才创建 `DerivedExport`；失败或中断由后续恢复在确认 owner 进程已不存在后按账本清理，不能留下可见半成品或无法归属的孤儿目录。重试创建新 attempt。首版不要求完整英文 HTML 看板或第二套事实库。

### FR-14：模拟面试与复习闭环

系统必须能基于当前岗位、项目材料和知识缺口生成模拟面试题、追问和回答要点。面试后只保存结构化复盘：题目/主题、掌握等级、薄弱点、摘要和下次复习日期。

复习记录必须同时保留其来源 PreparationRun 和稳定 `ReviewTarget`。指纹不得直接使用 ClaimRevision/KnowledgeGap ID 或题面，而应使用 canonical `ReviewSubjectProjection`：稳定 Claim ID + 结构化复习语义 hash，以及稳定 gap key + 缺口状态。纯措辞、展示顺序、行号或等价 Evidence 替换不应中断连续性；概念、机制、行为契约、取舍、实现/测试/冲突/证据时效、角色/结果锚点或缺口状态实质变化时，新材料必须标为“需要重新评估”。无法证明等价时保守重评；不同项目、作用域或知识主题不得模糊合并。

系统不得保存完整面试对话，也不得创建主动提醒、后台任务或自动消息。复习日期是用户主动回到 Skill 时可见的状态，不是调度指令。已发布 HTML/Markdown 保持其复习截点不变；Owner 可基于同一 ScanRun 显式创建新 PreparationRun 以获得新的复习投影，不必为此 refresh。

### FR-15：可见部分失败与诚实覆盖

权限不足、仓库损坏、无法识别项目、语言不支持、敏感文件排除或单个模块读取失败不得使其余可读项目的准备运行整体失败。每个问题必须显示至少包含路径/范围、原因、影响和可采取的补救动作的 ScanIssue。

若 `workspace_path` 本身不可读，运行必须以明确错误终止；若工作区可读但没有发现项目，系统必须产生空覆盖报告和下一步提示，而不是声称项目分析完成。

## 4. 非功能需求

### NFR-01：本地授权、只读与最小网络边界

GoodJob 的访问边界分为三层，缺一不可：

1. `workspace_path` 只授权 Python 在本机读取指定根内的合资格内容；显式 JD 只作为岗位输入读取，不扩展扫描范围。
2. 每个显式会话的 `AuthorizationReceipt(source_analysis)` 才授权 GoodJob 让当前 host agent 会话分析该工作区。回执只记录 scope、notice、确认时间与当前 task capability 的 digest；原始 capability 由 host agent task 易失编排状态持有，每次受保护请求经平台私有能力通道传给本地核心并 constant-time compare，不落库、不记日志、不能从旧 receipt 恢复。能力缺失或运行时不支持时必须重新确认。按证据打开的原文件会进入该会话的模型处理链路；GoodJob 不扩大当前产品/账户/工作区的数据处理与保留边界。
3. 工作区内 `.git` 标记只是根外 Git 目录的**不可信候选**。系统先只读取根内标记并展示 marker kind 与精确候选；Owner 对这些候选授予 `external_git_relation_probe` 后，系统才可解析规范化 git-dir/common-dir、互指关系和目录身份。系统展示解析结果和拟读取字段后，还须取得同时绑定精确路径与身份的 `AuthorizationReceipt(external_git_metadata)`，才能以描述符直接读取关系与 HEAD/ref。外部阶段不得启动 Git；根外 index/dirty、源码、配置、模块、blob、diff 和 Git 历史都不得被扫描或读取。

GoodJob 不得写入、格式化、构建、测试、提交或以其他方式改变被扫描项目，也不得引入当前 host agent 会话之外的外部分析服务、源码上传通道、遥测或扫描网络依赖。

### NFR-02：最小化证据保存与可核验性

个人数据库保存路径、定位、哈希、状态、来源类型和短摘要等证据指针，不保存完整源码、完整函数体或大段文档快照。每个关键 Claim 至少关联一个 Evidence；强结论优先使用相互独立的代码、测试、配置、文档或用户背景交叉支撑。

### NFR-03：离线可用的静态产物

生成后的 HTML 必须在断网、无本地服务的环境中打开并完成本地浏览、筛选和证据展开。产物所需脚本、样式、字体和图标必须随本地产物提供，不得依赖远端 CDN。

### NFR-04：可重现与不破坏历史

每个准备快照必须记录其输入、RoleLens、证据版本和复习状态截点，使材料可以说明“基于什么事实生成”。增量刷新不得破坏历史快照或用户回答；变化文件导致的旧证据必须显式失效并重建。prepare 的预检、读取前检查或提交前检查发现所用 SourceRevision 已变化时，运行必须以 `refresh_required` 终止；不得隐式 refresh、半提交分析或改写旧快照。

### NFR-05：可见降级与可恢复性

局部问题必须结构化呈现而不是静默跳过。系统可以输出部分结果，但不得把部分覆盖标注为完整。进程中断、Owner 取消、写者繁忙、渲染和英文导出中断必须有明确状态；进程型运行以 PID+启动标识判断中断，PreparationRun 只由同一 SessionCapability 续接，新 task 需 Owner 明示 `abandon_and_restart`。恢复只能清理账本预登记路径，不得依赖超时删锁、目录猜测或模型内存续跑。

### NFR-06：Skill 与个人状态隔离

版本化 Skill 仅承载流程、脚本、参考材料和前端资源。SQLite、工作区注册、授权回执、访谈答案、快照、复习状态和导出材料必须保存在个人数据目录；Skill 更新、重装或未来发布不能覆盖这些状态，也不能把它们纳入 Git 仓库。首版不自动删除、归档或淘汰个人历史；每次 scan/prepare 必须显示 SQLite、artifacts、exports、drafts 的占用量与快照数量，未来清理能力另行决策。

### NFR-07：可扩展但不虚假泛化

岗位机制必须允许未知岗位名称通过动态 RoleLens 工作，语言机制必须允许以后新增适配器；首版对未深读语言只承诺基础档案和明确边界，不伪装成完成了深层调用或语义分析。

### NFR-08：不可信输入与安全呈现

工作区文件、Git 元数据、JD、项目名称、用户项目上下文和模型生成文本一律作为不可信数据处理，不能改变 Skill 指令、AuthorizationReceipt、授权根、工具权限、网络边界或写入目标。`.git` 的 `gitdir:`、`commondir`、Git 配置和继承的 `GIT_*` 环境变量均不能自行授权根外读取。扫描器不得通过 import、构建脚本、包管理器、shell 拼接或其他方式执行项目内容；离线 HTML 必须把项目数据作为文本或经安全编码的结构化数据呈现，不得执行其中的 HTML、脚本、事件处理器或 URL。

### FR-16：跨平台 Git 沙箱与进程身份

GoodJob 必须在 macOS 和 Linux（含 WSL2）上以各自平台的等价安全沙箱运行 Git 子进程，而不是只在单一平台可用。macOS 使用 `sandbox-exec` Seatbelt 沙箱，Linux 使用 `bwrap`（bubblewrap）沙箱；两者都必须拒绝 Git 网络访问、只读授权根、禁用 hooks 和可变 Git 配置。任一平台的沙箱后端不可用时必须 fail-closed，不回退到无沙箱模式。

进程身份（用于崩溃恢复的 PID 重用防护）在 macOS 上使用 BSD `ps` 的启动时间，在 Linux 上读取 `/proc/<pid>/stat` 的 starttime 字段。两者必须满足同一契约：同一进程的标识稳定，PID 重用时标识变化。

WSL1 不支持用户命名空间（bwrap 依赖），因此 WSL1 上 bwrap 后端 fail-closed；只有 WSL2 提供完整沙箱。原生 Windows 不在本 FR 范围内。

**验收结果：** 在 macOS 和 Linux（含 WSL2）上分别能运行完整 scan/prepare 流程，Git 子进程被各自平台的沙箱限制；任一沙箱后端缺失时明确报错且零 Git 执行。

### FR-17：Host Agent 无关会话

通过 `--agent-runtime` 参数标识宿主运行时；`issuer_kind` 为自由文本，默认 `codex_task_runtime` 保持向后兼容；`uv` 不存在时自动回退到 `python3.12`。每个宿主在请求源码授权前必须能通过同一个 `--preflight-only` 入口取得 `launcher-preflight-v1`：它用固定 check、notice 与 remediation 说明当前环境能否启动 broker，不要求宿主识别操作系统分支。预检不得读取工作区源码、创建个人状态或启动 broker；需要安装或提权时只报告用途并等待 Owner 明示同意。

**验收结果：** ready 时 stdout 只有一份 accepted v1、stderr 为空并退出 `0`；not-ready 时同样只在 stdout 返回 accepted v1 并退出 `2`。普通启动成功保持 launcher 静默；broker 建立前失败只在 stderr 返回 accepted v1，不把自由文本或协议损坏误判成可继续。

### FR-18：原生 Windows 安全运行时

GoodJob 在原生 Windows 上必须以独立的安全后端完成与现有平台相同的可观察安全结果：Git 远程访问和 helper 绕过失败而本地白名单操作正常；Git 与业务子进程在用户代码执行前进入可回收边界且不能逃逸；扫描器全部文件操作保持授权根身份并拒绝路径穿越、reparse、别名、ADS 与跨卷逃逸；SessionCapability 与私有 payload 只进入目标子进程的最小能力集合，不进入参数、环境变量或持久状态；输出总量受同一预算约束，失败后不遗留活动子进程、网络规则或系统资源。

上述结果的 Windows 实现机制由已接受的 [ADR-0011](../30-decisions/adrs/ADR-0011-native-windows-security-contract.md) 与 [ADR-0012](../30-decisions/adrs/ADR-0012-windows-nt-rename-and-directory-enumeration-correction.md) 决策链共同定义，产品需求不允许实现用不同机制弱化这些结果。

在 `IMP-31` 全部真机 E2E 通过前，原生 Windows 必须保持 unsupported / fail-closed，运行前提示推荐 WSL2；文档冻结或原语 spike 通过都不能提前改变支持状态。

**验收结果：** 原生 Windows 只有在 Git 网络隔离、进程树回收、授权根文件访问、capability 隔离、有界输出和异常清理均有真机阳性/负向证据后才进入支持矩阵；否则零受保护 Git/扫描执行并显示 WSL2 指引。

### NFR-09：跨平台沙箱等价性与 fail-closed 边界

macOS Seatbelt 和 Linux bwrap 沙箱在安全语义上必须等价：都拒绝网络、限制文件系统读取范围、隔离进程命名空间。两者的安全差异（bwrap 额外只读挂载 `/usr`、`/lib`、`/etc` 等系统路径以使 Git 二进制和身份解析可用）必须在 ADR-0009 中记录并接受。

平台后端选择在运行时按 `sys.platform` 自动决定，不提供手动覆盖。沙箱后端不存在（`sandbox-exec` 缺失或 `bwrap` 未安装/无法运行）时必须 fail-closed，不得回退到无沙箱或弱化沙箱。bwrap 已安装但无法运行（如 WSL1 的用户命名空间限制、AppArmor 限制、容器环境）时也必须 fail-closed 并给出安装/启用指引。

### NFR-10：宿主兼容性探针准入

每个宿主 agent 必须通过 5 项探针（发现路径、长驻 stdin、JSONL 往返、退出清理、真机 E2E）后才可进入支持矩阵；未通过者明确标注待支持。

### NFR-11：Windows 降级预算与 fail-closed 边界

原生 Windows 唯一允许的安全降级是 Git 子进程没有文件系统读隔离，因而可能读取授权根外的本机文件；该限制即使在未来准入后，也必须在每次原生 Windows 运行前清楚提示。要求完整 Git 文件系统隔离时应使用 WSL2。

Git 网络隔离、扫描器授权根/reparse/TOCTOU 边界、进程树回收和 capability 隔离不得降级。任一原生 Windows 安全前置条件不可用、无权限、无法验证或无法收窄到本次请求时，相关操作必须在受保护执行前 fail-closed；不得静默切换到无网络隔离、路径名重解析、非受控进程启动或宽泛能力继承。

正常结束、失败、取消和超限都不得遗留活动子进程、临时网络边界或未释放系统资源；stdout/stderr 必须共用一个端到端累计预算，不允许任一阶段形成无界缓冲。具体机制由 [ADR-0011](../30-decisions/adrs/ADR-0011-native-windows-security-contract.md) 与 [ADR-0012](../30-decisions/adrs/ADR-0012-windows-nt-rename-and-directory-enumeration-correction.md) 决策链定义，清理顺序仍由 ADR-0011 定义。

## 5. 关键失败路径

| 情况 | 用户可见行为 | 是否继续 |
| --- | --- | --- |
| 工作区根不存在或不可读 | 明确输入错误，指出路径与修复方式，不生成伪造材料 | 否，等待新的有效输入 |
| 源码分析授权未确认、被拒绝或提示版本已变化 | 显示规范化工作区、处理类别和当前会话边界提示；不创建新 ScanRun/PreparationRun | 否，等待本会话明确确认 |
| SessionCapability 丢失、digest 不匹配或进入新的 host agent task | receipt ID 不能单独通过；活动 PreparationRun 不能续接模型内存 | 重新确认；Owner 明示 abandon/restart 后复用终态快照与持久上下文 |
| 指定 JD 文件不可读 | 明确指出 JD 无法使用；用户可改正，或明确选择无 JD 模式 | 不自动忽略 JD |
| 根外 Git 元数据未授权或绑定校验失败 | 记录 `external_git_not_authorized`、`untrusted_git_pointer` 或关系不匹配 ScanIssue；不读取目标派生数据 | 是，作为可见覆盖缺口继续根内范围 |
| 岗位名称未知或无 JD | 生成带假设的候选 RoleLens，并在准备包中展示假设 | 是 |
| 某项目/模块权限不足或仓库损坏 | 记录 ScanIssue、覆盖影响和补救动作 | 是，继续其余范围 |
| 语言未深读支持 | 生成基础档案并标注分析边界 | 是 |
| 原生 Windows 尚未完成 `IMP-31` 准入，或任一原生 Windows 安全前置条件失败 | 标记 unsupported / fail-closed，零受保护 Git/扫描执行，明确推荐 WSL2 | 否，不降级执行 |
| 原始证据已移动或哈希失效 | 运行标记 `refresh_required`，列出受影响 SourceRevision，要求显式 refresh 或重新读取原文件 | 否，本次准备不得半提交；旧快照仍可读取 |
| 英文导出失败或进程中断 | ExportAttempt 标为 failed/interrupted；只清理该 attempt 预登记路径 | 是，可创建新 attempt 重试；中文快照/latest 不变 |
| 缺少业务、结果或个人职责信息 | 产生项目级批量访谈问题；用户跳过后保留缺口 | 是 |
